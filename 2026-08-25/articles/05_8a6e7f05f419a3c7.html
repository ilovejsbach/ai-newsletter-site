구글, 에이전트용 P2P 망 SAM 공개

AI 에이전트가 여러 장소에서 함께 일하려면 도구와 권한을 안전하게 나눠야 한다. 지금은 이를 위해 내부 스크립트나 모델 엔드포인트를 인터넷에 드러내는 경우가 많다. 구글은 이 문제를 줄이려는 오픈소스 네트워킹 프로젝트 SAM을 내놨다. 대상은 클라우드, 사내 데이터센터, 노트북, 모바일 기기에 흩어진 에이전트다.

핵심 브리핑

SAM은 자율형 AI 에이전트가 서로의 도구를 안전하게 공유하도록 만든 P2P 네트워크다. 내부 도구를 공용 인터넷에 열지 않고도 에이전트끼리 연결하게 하려는 목적이 있다. 구조는 사설 VPN에 가깝지만, 용도는 MCP 기반 도구 공유에 맞췄다.

노드는 서로를 자동으로 찾는다. NAT 환경에서도 연결을 유지한다. 각 요청은 암호학 방식으로 권한을 확인한다. 다만 저장소에는 공식 지원 제품이 아니라는 문구가 붙어 있다. 공개 메시는 아직 베타 테스트넷으로 표기돼 있다.

  • 배포물은 Go 바이너리, 설치 스크립트, ghcr.io Docker 이미지다
  • charts/sam-mesh Helm 차트와 Kubernetes 운영 가이드가 있다
  • Android와 iOS도 지원한다
  • 공개 테스트넷 주소는 bananas.sam-mesh.dev다
  • 실제 업무는 제어 평면을 직접 운영하는 DIY Mode를 권장한다

구성 요소는 세 가지 바이너리로 나뉜다. sam-control-plane은 신원 등록, 토큰 발급, 정책 배포를 맡는다. sam-router는 libp2p 부트스트랩과 GossipSub 라우팅 오버레이를 맡는다. sam-node는 P2P 전송, 자가 복구 연결, 로컬 MCP HTTP 인터페이스를 제공한다.

노드는 sam-node join으로 가입한다. 이후 sam-node run으로 실행한다. libp2p는 기본으로 5001/udp와 5002/tcp를 쓴다. 로컬 MCP API 기본 포트는 8080이다.

권한을 주고받는 방식도 꽤 구체적이다. 제어 평면은 OIDC JWT를 검증한 뒤, 그 안의 클레임을 Datalog 사실로 바꿔 Biscuit 토큰에 넣는다. 이렇게 만든 토큰을 각 노드가 로컬 규칙으로 검사한다. 노드는 중앙 서버에 다시 묻지 않고 오프라인으로 권한을 판단한다.

기본 정책은 강한 기본 거부다. granted_service_exact(...) 같은 명시 권한이 있어야 접근할 수 있다. 예외는 기본 제공하지 않는다. 서비스 탐색용 system://sam.catalog도 따로 허용해야 한다. 서비스 이름은 type://name 형식을 쓰고 와일드카드도 지원한다.

스펙과 도입 조건

도입 조건은 비교적 분명하다. 문서는 중견·대기업 엔지니어링 조직을 주 대상이라고 적었다. 특히 클라우드, 데이터센터, 노트북처럼 네트워크 경계가 둘 이상인 환경에 맞는다. 단일 VPC 안에서만 에이전트를 돌리는 스타트업은 얻는 이익이 작을 수 있다.

규제 산업도 주요 대상으로 제시했다. 금융 서비스, 헬스케어, 공공, 국방, 산업 현장과 로보틱스 엣지 운영이 여기에 포함된다. 공통점은 내부 도구를 인터넷에 공개하기 어려운 조직이라는 점이다.

보안 집행은 두 단계로 이뤄진다. 1단계는 차단과 폐기 캐시로 연결을 막는다. 2단계는 Biscuit authorizer를 정확히 두 번 실행한다. 먼저 노드 자신의 신원 토큰으로 target_fact를 만든다. 그다음 호출자 토큰을 검사한다. 재전송 공격은 연결 peer ID와 토큰의 값이 일치해야 통과하도록 막는다.

운영자는 로컬 규칙으로 권한을 더 좁힐 수 있다. 예를 들어 오후 9시 이후 쓰기 도구를 막거나 외주 인력을 차단할 수 있다. 반대로 로컬 허용 규칙이 있어도 제어 평면의 if 제약을 넘을 수는 없다.

외부 통신 통제용 구성도 있다. nano-init은 샌드박스에서 PID 1로 실행되며 프록시 환경 변수를 심는다. 이를 무시하는 도구는 C의 connect() 호출을 가로채 80과 443 포트 연결을 통제한다. 트래픽은 Unix domain socket으로 sam-box에 닿고, 게이트웨이는 Biscuit을 검증한 뒤 secrets.yaml의 실제 자격 증명을 넣어 HTTPS로 올린다. 에이전트 샌드박스에는 키가 남지 않는다.

업계의 움직임

공개 반응으로 확인되는 내용은 아직 제한적이다. 문서는 Gemini, Claude Code, Claude Desktop, Google Antigravity, OpenClaw 연동 가이드를 함께 제시했다. 구글은 단순 데모보다 실제 에이전트 도구 생태계 연결을 먼저 보여주려 한 셈이다.

시사점과 체크포인트

우리 회사가 에이전트를 여러 망에서 운영하려면, 모델 성능보다 먼저 연결 구조를 정리해야 한다. 사내 API를 외부에 공개하지 않고 도구를 붙일 수 있는지 검토할 만하다.

검토 포인트는 분명하다.

  • IAM·SSO 팀은 OIDC 기반 신원 검증을 기존 체계와 맞출 수 있는지 본다
  • 플랫폼 팀은 Kubernetes, Docker, 모바일 단말까지 운영 범위를 감당할지 따져본다
  • 보안 팀은 기본 거부 정책을 서비스 단위 권한 관리와 연결할 방법을 정리한다
  • 개발 조직은 MCP 도구 목록을 먼저 자산화해야 한다

주의할 점도 있다. 공개 메시는 베타 테스트넷이다. 공식 지원 제품도 아니다. 실제 업무는 제어 평면을 직접 운영하라고 문서가 적었다. 도입 검토 때는 성능보다 운영 책임과 장애 대응 범위를 먼저 확인하는 편이 낫다.

주요 용어

제로 트러스트(Zero Trust): 네트워크 안팎을 믿지 않고 요청마다 신원과 권한을 확인하는 보안 방식 P2P(Peer-to-Peer): 중앙 서버를 거치지 않고 장치끼리 직접 연결하는 통신 구조 MCP(Model Context Protocol): 모델이나 에이전트가 외부 도구를 공통 방식으로 호출하는 규약 OIDC(OpenID Connect): 로그인 신원을 다른 서비스가 검증할 때 쓰는 표준 방식 Biscuit: 권한 조건을 토큰에 담아 오프라인으로 검사할 수 있게 만든 인증 토큰 방식
