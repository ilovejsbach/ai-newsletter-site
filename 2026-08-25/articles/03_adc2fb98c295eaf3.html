OpenAI, Codex를 앱 속 에이전트 틀로 넓혔다

OpenAI는 Codex를 하나의 앱이 아니라, 다른 제품 안에 넣을 수 있는 실행 틀로 설명했다. 핵심은 모델이 아니라 하네스다. 이 하네스가 문맥 유지, 도구 호출, 승인 요청, 작업 재개를 맡는다.

핵심 브리핑

OpenAI는 Codex 앱, CLI, IDE 확장 뒤에서 같은 오픈소스 하네스가 동작한다고 밝혔다. 이 하네스는 모델이 작업 문맥을 모으고, 여러 단계로 추론하고, 도구를 쓰고, 경계 안에서 실행되도록 돕는다. 개발팀은 이 틀을 가져다 자사 제품과 워크플로에 붙일 수 있다.

OpenAI는 강한 에이전트가 프롬프트와 응답만으로는 부족하다고 설명했다. 작업 이해, 장기 문맥 유지, 관련 정보 확인, 도구 호출, 실패 처리, 사람 승인 요청, 결과 반환이 함께 필요하다는 뜻이다. 이 실행 계층이 바로 하네스다.

Codex 하네스는 대화 상태 관리, 실행 스트리밍, 도구 사용, 샌드박스와 승인 정책 적용, 여러 턴에 걸친 작업 지속을 맡는다. Codex app-server는 이를 문서화된 클라이언트 프로토콜로 노출한다. 앱은 스레드를 만들고, 턴을 시작하고, 이벤트를 받고, 승인 요청을 처리할 수 있다.

OpenAI는 통합 방식도 나눠 제시했다.

  • 스크립트나 CI 작업에는 codex exec를 쓴다
  • 프로그램 코드에서 작업을 시작하거나 재개하려면 Codex SDK를 쓴다
  • 제품 자체에 에이전트를 넣으려면 Codex app-server를 쓴다

OpenAI는 ARC-AGI-3에서 하네스 설계가 결과를 크게 바꿨다고 밝혔다. retained reasoning과 context compaction을 적용하자 GPT‑5.6 Sol 점수가 13.3%에서 38.3%로 올랐다. 출력 토큰은 6분의 1로 줄었다.

주요 트렌드

이번 발표는 모델 API를 파는 데서 한 걸음 더 나아간다. OpenAI는 범용 코딩 비서로 사용자를 끌어오는 대신, 기존 제품 화면 안에 Codex를 심는 구조를 밀고 있다. 대시보드, 기록 화면, 승인 흐름 같은 업무 맥락을 애플리케이션이 계속 쥐는 방식이다.

오픈소스 전략도 분명하다. OpenAI는 CLI, app-server, 공식 SDK를 공개 컴포넌트로 제공한다. 다만 오픈소스로 여는 부분은 하네스와 통합 표면이고, 모델 접근과 관리형 서비스는 별개로 남긴다고 선을 그었다.

업계의 움직임

공개 사례도 이미 나왔다. GitHub와 JetBrains는 기존 IDE 흐름에 Codex를 넣고 있다. Cisco는 Cisco Cloud Control 안의 App Builder에서 Codex SDK를 쓴다. Thrive Holdings와 Crete는 세무 준비 워크플로에 Codex를 넣었고, 시범 운영에서 7,000건의 신고를 처리하며 준비 시간을 약 3분의 1 줄였다.

시사점과 체크포인트

우리 회사가 볼 부분은 코딩 지원보다 업무 시스템 통합이다. 운영 대시보드, 고객 지원 콘솔, 보안 조사 화면, 내부 결재 화면에 에이전트를 붙일 수 있다면 비개발 조직도 바로 쓸 수 있다.

도입 검토 때는 다음을 따져야 한다.

  • 어떤 시스템이 문맥과 기록의 원본이 될지
  • 승인 요청을 현행 결재 체계와 어떻게 맞출지
  • 에이전트가 접근할 파일과 도구 범위를 어디까지 열지
  • 중단, 재개, 실패 처리 로그를 어떻게 남길지

OpenAI가 제시한 수치는 하네스 설계 효과를 보여주지만, 특정 벤치마크 결과다. 우리 업무에 맞는 성과는 별도 검증이 필요하다. 오픈소스 컴포넌트와 별도인 모델 접근 조건도 계약 단계에서 따져봐야 한다.

주요 용어

하네스(Harness): 모델 실행, 도구 호출, 승인 처리, 상태 유지를 맡는 실행 계층 SDK(Software Development Kit): 응용프로그램이 기능을 붙일 때 쓰는 개발 도구 묶음 샌드박스(Sandbox): 허용된 범위 안에서만 실행되게 제한한 환경 MCP(Model Context Protocol): 모델에 도구와 문맥을 연결하는 방식 ARC-AGI-3: 추론 능력을 재는 벤치마크
