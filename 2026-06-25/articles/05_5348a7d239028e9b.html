클로드 오퍼스 4.8, 정직성과 장기 작업 강화

Claude Opus 4.8 발표는 새 모델 하나만의 이야기가 아니다. 앤트로픽은 이번 버전을 코딩과 에이전트 작업에서 더 믿을 수 있는 협업자로 포지셔닝하면서, 이를 뒷받침하는 사용 제어 기능도 같이 내놨다. 성능 향상은 ‘소폭이지만 체감되는 개선’이라고 비교적 절제해 표현한다. 대신 정직성(honesty), 장기 작업 지속성, 대형 코드베이스 단위 작업 처리 같은 실사용 지점을 더 강하게 밀고 있다.

원문이 말하는 핵심

Opus 4.8은 Opus 4.7을 기반으로 한 업그레이드 모델로, 코딩, 에이전트 작업, 전문 업무 전반에서 개선됐다고 소개된다. 가격은 그대로 유지된다. 함께 발표된 기능으로는 claude.ai의 노력 제어, Claude Code의 동적 워크플로, 그리고 Opus 4.8 fast mode가 있다. 모델 단독 성능보다 사용 방식과 운영 폭을 넓힌 릴리즈에 가깝다.

무엇이 달라졌나

가장 두드러지는 변화는 ‘정직성’에 대한 강조다. 앤트로픽은 AI 모델이 근거가 빈약한데도 진척을 자신 있게 주장하는 문제가 있는데, Opus 4.8은 불확실성을 더 잘 표시하고 뒷받침되지 않은 주장을 덜 한다고 설명한다. 내부 평가에서는 작성한 코드의 결함을 그냥 넘기는 비율이 전작보다 약 4배 낮다고 밝혔다. 또 정렬 평가에서는 사용자 자율성 지원, 사용자 최선 이익 지향 같은 친사회적 특성에서 새 최고 수준을 기록했다고 적었다.

장기 실행형 작업을 위한 기능

동적 워크플로는 연구 프리뷰 형태로 Claude Code에 추가되며, 한 세션 안에서 수백 개의 병렬 서브에이전트(subagent)를 돌려 매우 큰 작업을 처리하도록 설계됐다. 모델이 작업 계획을 세우고 실행한 뒤, 결과를 검증하고 사용자에게 보고하는 흐름이다. 예시로는 수십만 줄 코드베이스 전반의 마이그레이션을 시작부터 머지(merge) 직전까지 수행하는 시나리오가 제시됐다. 이 기능은 Enterprise, Team, Max 플랜의 Claude Code에서 제공된다고 한다.

토큰·속도·API 측면 변화

claude.ai와 Cowork에는 응답에 들이는 노력 수준을 조정하는 컨트롤이 추가됐다. 높은 노력 설정에서는 더 자주, 더 깊게 생각해 응답 품질을 높이고, 낮은 설정에서는 더 빠르게 응답하며 사용자의 rate limit 소모를 줄인다. Opus 4.8 기본값은 high effort이며, extra 또는 max를 선택하면 더 많은 토큰을 써 더 나은 결과를 추구할 수 있다고 안내한다. Messages API는 messages 배열 내부에 system entries를 허용해, 작업 도중 권한·토큰 예산·환경 문맥을 갱신해도 프롬프트 캐시를 깨지 않게 했다.

가격과 배포 방식

정규 사용 가격은 Opus 4.7과 동일하게 입력 100만 토큰당 5달러, 출력 100만 토큰당 25달러다. fast mode 가격은 입력 100만 토큰당 10달러, 출력 100만 토큰당 50달러로 제시됐다. fast mode는 2.5배 속도에서 동작하며, 이전 모델 대비 3배 저렴해졌다고 설명한다. 개발자는 Claude API에서 claude-opus-4-8 이름으로 사용할 수 있다.

맥락과 차별점

이번 발표는 경쟁 모델 대비 절대 우위를 과하게 단정하기보다, 장기 협업에서의 안정성과 사용 제어를 메시지 중심에 놓는다. 특히 코드 생성 정확도보다 ‘잘 모를 때 모른다고 하는가’, ‘긴 작업 동안 엇나가지 않는가’가 차별화 포인트로 제시된다. 또 더 높은 지능의 새 클래스 모델로 Mythos 계열을 예고하면서도, 사이버 보안 수준의 안전장치가 더 필요해 일반 공개 전이라고 선을 그었다. 모델 확장과 안전 통제를 분리하지 않겠다는 신호로 읽힌다.

실무 영향과 아직 볼 점

사내 개발팀에는 Claude Code의 동적 워크플로와 mid-task system update가 실제 에이전트 하네스 설계에 꽤 실용적일 수 있다. 권한이나 토큰 예산을 작업 중간에 바꾸면서도 캐시를 유지하는 기능은 장기 작업형 코딩 보조에 유용하다. 다만 본문 발췌만으로는 벤치마크 표의 전체 수치와 특정 경쟁 모델 대비 조건을 모두 확인하기 어렵다. 결국 도입 판단은 장기 코드 수정, 테스트 통과율, 비용 대비 생산성, 거짓 진척 보고 감소 같은 운영 지표로 다시 검증해야 한다.
