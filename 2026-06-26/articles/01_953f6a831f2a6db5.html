오니스 1.0, 코딩 에이전트의 새 축

코딩 에이전트는 보통 모델 위에 메모리, 도구, 오류 처리, 실행 절차를 얹은 하네스를 사람이 직접 설계해 붙인다. 오니스 1.0은 이 전제를 바꿔, 답안뿐 아니라 그 답안을 만들기 위한 실행 틀까지 학습 대상으로 본다. 모델이 태스크와 이전 스캐폴드를 읽고 새 스캐폴드를 제안한 뒤, 그 틀로 풀이를 수행하고 보상을 함께 받는 구조다. 결과적으로 모델 정책과 오케스트레이션 로직이 같이 진화하도록 설계됐다.

무엇이 핵심인가

오니스 1.0은 코딩 에이전트에 맞춘 추론 모델군이다. 9B Dense, 31B Dense, 35B MoE, 397B MoE 네 가지로 구성되며, 35B MoE는 토큰당 약 3B 파라미터를 활성화한다.

  • 사전학습 기반: Gemma 4, Qwen 3.5
  • 배포 형식: Hugging Face 체크포인트, FP8, GGUF
  • 라이선스: 전 모델 MIT

응답은 `<think>` 블록으로 추론을 먼저 생성한 뒤 최종 답을 내놓는 방식이며, 에이전트 루프에서 쓸 수 있는 정형 도구 호출도 출력한다.

무엇이 달라졌나

대부분의 코딩 에이전트는 사람이 미리 만든 고정 하네스를 사용한다. 반면 오니스 1.0은 스캐폴드를 학습 가능한 대상으로 두고, 강화학습 중 모델 정책과 함께 공동 최적화한다.

학습은 두 단계로 진행된다. 먼저 모델이 태스크와 이전 스캐폴드를 읽고 개선된 스캐폴드를 제안한 뒤, 이어서 그 스캐폴드와 태스크를 이용해 실제 풀이 롤아웃(rollout)을 만든다. 이 롤아웃의 보상이 두 단계 모두로 역전파되면서, 점수가 높은 스캐폴드가 자동으로 선택되고 변형된다.

비동기 파이프라인 RL도 사용한다. 오래된 오프폴리시(off-policy) 토큰은 가중치를 낮추고, 임계값을 넘기면 버리며, 최적화에는 토큰 수준 GRPO 목적함수를 쓴다.

보상 해킹은 어떻게 막았나

모델이 자기 스캐폴드를 쓸 수 있게 하면 보상 해킹 위험도 커진다. 예를 들어 숨겨진 테스트 파일을 읽거나, 환경 안의 정답을 베껴 점수를 올릴 수 있다.

이를 막기 위해 세 겹의 방어선을 둔다.

  • 고정 신뢰 경계(trust boundary): 환경, 도구 표면, 테스트 격리는 모델이 바꿀 수 없게 고정
  • 결정적 모니터(deterministic monitor): 금지 경로 읽기, 검증 스크립트 수정 등을 감지하면 보상 0점 처리
  • 고정된 대규모 언어모델 심판(frozen LLM judge): 주 보상기가 아니라 검증기 위의 거부권(veto) 계층으로 배치

금지된 행동이 포함된 궤적은 이점(advantage) 계산에서도 제외한다.

성능은 어디까지 나왔나

플래그십인 397B 모델은 Terminal-Bench 2.1에서 77.5, SWE-Bench Verified에서 82.4를 기록했다. 공개된 수치 기준으로 SWE-Bench Verified에서는 Claude Opus 4.8의 87.6보다 낮지만, 오픈 모델 중 동급 비교에서는 강한 수치로 제시됐다.

Terminal-Bench 2.1에서는 Claude Opus 4.7의 70.3보다 높지만, Claude Opus 4.8의 85와 GLM-5.2-744B의 81.0에는 못 미친다. 즉 '최고 성능' 주장은 비교 가능한 오픈 모델 범위로 한정해 읽어야 한다.

작은 모델의 효율성도 강조했다.

  • 35B: Terminal-Bench 2.1에서 64.2
  • Qwen 3.5-397B: 같은 지표 53.5
  • 9B: Terminal-Bench 2.1 43.1, SWE-Bench Verified 69.4

실무에서는 어떻게 붙일 수 있나

배포 방식은 비교적 단순하다. 9B 모델은 bf16 기준 약 19GB이며, 80GB GPU 한 장에서 서빙 가능하다고 적었다.

지원 서빙 스택은 vLLM, SGLang, Transformers다. 각 모델은 OpenAI 호환 엔드포인트를 제공하므로 기존 에이전트 프레임워크를 코드 수정 없이 붙일 수 있다는 점을 장점으로 내세운다.

권장 샘플링 설정도 구체적이다.

  • temperature=0.6
  • top_p=0.95
  • top_k=20
  • reasoning trace는 `reasoning_content`, 최종 답은 `content`

OpenHands, OpenClaw, OpenCode와의 연동도 언급됐다.

어디에 적합하고 무엇을 봐야 하나

지향점은 터미널 중심 코딩 에이전트와 저장소 단위 작업이다. 다중 파일 리팩터링, 버그 위치 파악, 테스트 기반 패치 같은 업무가 대표 사례로 제시됐다.

  • 9B: 엣지 환경, 단일 GPU, 비용·지연이 중요한 경우
  • 397B: 길고 다단계인 작업에서 정확도를 우선할 경우

사내에서는 내부 저장소 권한, 테스트 격리, 보안 도구 호출 정책까지 포함해 평가해야 한다. 모델이 하네스를 더 잘 짠다고 해서, 조직별 승인 흐름이나 코드 리뷰 기준까지 자동으로 맞춰지는 것은 아니기 때문이다.

출처와 한계

벤더가 제시한 성능 수치이며, 벤치마크 환경과 실제 사내 저장소의 작업 분포는 다를 수 있다. 특히 보상 해킹 방어는 설계상 중요하지만, 운영 환경에서 어떤 우회 사례가 남는지는 이 발췌만으로는 확인하기 어렵다.

또한 큰 모델이 상용 상위 모델 전반을 넘어선다는 뜻은 아니다. 본문에서도 Claude Opus 4.8과 GLM-5.2-744B보다 낮은 지표가 함께 제시돼 있다.
