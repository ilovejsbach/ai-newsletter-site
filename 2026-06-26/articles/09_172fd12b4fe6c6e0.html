제미니 3.5 플래시, 컴퓨터 사용 내장

검색이나 함수 호출만으로는 처리하기 어려운 작업이 있다. 실제 화면을 보고 클릭하고 입력해야 하는 브라우저·앱 자동화가 그렇다. Gemini 3.5 Flash는 이 컴퓨터 사용 기능을 별도 모델이 아니라 기본 내장 도구로 가져오면서, 하나의 주 모델로 보고·추론하고·행동하는 에이전트를 만들 수 있게 했다. 대신 기능이 강해진 만큼 안전장치도 선택형 옵션과 운영 권고 형태로 같이 제시됐다.

원문이 말하는 핵심

컴퓨터 사용은 이제 Gemini 3.5 Flash의 기본 내장 도구다. 이전에는 독립된 Gemini 2.5 computer use 모델에서만 가능했지만, 이제 메인 Flash 모델 안에서 같은 계열 기능을 쓸 수 있게 됐다.

Google은 이를 통해 개발자가 브라우저, 모바일, 데스크톱 환경을 넘나드는 맞춤형 에이전트를 더 안정적으로 만들 수 있다고 설명한다. 기존의 Search, Maps grounding 같은 내장 도구에 더해, 실제 UI 상호작용이 모델의 기본 도구셋에 들어온 셈이다.

무엇이 달라졌나

변화의 핵심은 분리된 전용 모델에서 메인 범용 모델로의 통합이다. 이는 모델 선택과 배선이 단순해진다는 뜻이기도 하다.

Google은 Gemini가 원래 함수 호출과 내장 도구 사용에 강했고, 여기에 컴퓨터 사용을 더하면서 장기 작업과 엔터프라이즈 자동화 성능이 개선됐다고 설명한다. 사례로는 지속적인 소프트웨어 테스트와 전문 애플리케이션을 가로지르는 지식 업무가 제시됐다.

즉 단일 모델이 API 호출형 업무와 UI 조작형 업무를 함께 다루는 방향이다.

안전은 어떻게 다루나

라이브 환경에서 작동하는 에이전트는 간접 프롬프트 주입 위험이 크다. 이를 줄이기 위해 Gemini 3.5 Flash의 컴퓨터 사용에는 표적 적대적 훈련(targeted adversarial training)을 적용했다고 설명한다.

추가로 엔터프라이즈용 선택형 보호장치 두 가지를 같이 공개했다.

  • 민감하거나 되돌릴 수 없는 작업에 대해 명시적 사용자 확인 요구
  • 간접 프롬프트 주입이 감지되면 작업 자동 중단

이 두 기능은 필수가 아니라 옵션이다. 그래서 실제 안전성은 개발자가 어떤 운영 가드를 더 두느냐에 크게 좌우된다.

실무에서는 어디에 쓰일까

본문은 자체 예시로 Gemini 앱 기능을 분류하거나, 문서의 접근성 문제를 점검하는 장면을 보여준다. 이런 유형은 API 통합만으로는 어려운 대표 작업이다.

사내 관점에서는 다음 같은 흐름이 먼저 떠오른다.

  • 웹 콘솔 회귀 테스트
  • 내부 SaaS 운영 화면 점검
  • 정형화된 사무형 지식 업무 자동화

다만 화면 조작 기반 자동화는 DOM 변경, 인증 세션, 권한 상승, 예외 팝업 같은 변수가 많아, API형 에이전트보다 운영 난이도가 높다.

도입 경로와 운영 포인트

사용 경로는 Gemini API와 Gemini Enterprise Agent Platform 두 갈래다. 또한 Browserbase가 호스팅하는 데모 환경도 함께 안내됐다.

이 조합은 개발자 실험과 엔터프라이즈 운영을 분리해 보게 한다. 초기 검증은 데모·API로 빠르게 시작하고, 실제 운영은 엔터프라이즈 플랫폼에서 가드레일과 권한 정책을 붙이는 방식이 자연스럽다.

사내 적용 시에는 모델 성능보다 먼저 다음을 점검해야 한다.

  • 샌드박스 범위
  • 사용자 승인 UX
  • 세션 비밀정보 노출 방지
  • 실패 시 정지와 롤백 정책

출처와 한계

발췌에는 구체적인 벤치마크 수치나 가격, 컨텍스트 한도, 지원 OS 범위는 나오지 않는다. 따라서 기능 방향은 분명하지만, 실무 비교를 위해서는 별도 문서 확인이 필요하다.

또한 고객 사례가 언급되지만 세부 운영 지표는 제시되지 않는다. 도입 판단에는 내부 환경에서의 작업 성공률과 안전성 검증이 더 중요하다.
