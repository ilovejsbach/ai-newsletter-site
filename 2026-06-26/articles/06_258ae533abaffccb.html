허메스 에이전트, /learn으로 스킬 생성

에이전트가 같은 작업을 여러 번 반복한다면, 결국 필요한 것은 더 긴 메모리보다 재사용 가능한 절차 문서다. 허메스의 `/learn`은 그 절차 문서를 사람이 직접 쓰는 대신, 에이전트가 자료를 읽고 표준 형식의 `SKILL.md`로 정리하게 한다. 소스는 로컬 SDK, 웹 문서, 방금 끝낸 대화, 붙여넣은 메모까지 넓다. 핵심은 별도 인제스트 파이프라인이 아니라, 기존 도구와 대화 흐름 안에서 스킬을 만드는 데 있다.

원문이 말하는 핵심

허메스의 스킬은 필요할 때만 불러오는 지식 문서다. 각 스킬은 폴더 하나와 그 안의 `SKILL.md`로 구성되며, agentskills.io 오픈 표준과 호환된다고 적었다.

모든 스킬은 `~/.hermes/skills/` 아래에 모인다. 번들 스킬, 허브 설치 스킬, 에이전트가 새로 만든 스킬이 모두 여기에 저장되고, 설치된 스킬은 자동으로 슬래시 커맨드가 된다.

예를 들어 `/plan`, `/axolotl` 같은 명령을 실행하면 해당 스킬 지침이 현재 턴에 로드된다.

무엇이 달라졌나

이전에는 재사용 가능한 절차를 만들려면 사람이 `SKILL.md`를 직접 작성해야 했다. `/learn`은 그 단계를 없앤다.

사용자는 소스만 지정하면 된다.

  • 로컬 디렉터리: 코드, API 문서, 매뉴얼, PDF, 설정 파일
  • 온라인 문서 URL
  • 방금 수행한 대화 기반 워크플로
  • 붙여넣은 노트나 절차 설명

에이전트는 `read_file`, `search_files`, `web_extract` 같은 기존 도구로 자료를 모으고, 하우스 스타일에 맞는 스킬 문서를 작성한다. 존재하지 않는 명령을 지어내지 않는 것도 원칙으로 명시했다.

스킬은 어떻게 로드되나

허메스는 스킬을 항상 전부 컨텍스트에 넣지 않는다. 대신 세 단계 로딩으로 토큰 비용을 줄인다.

  • 항상 보는 것은 컴팩트한 인덱스
  • 실제 태스크가 필요할 때만 전체 스킬 본문 로드

이 진행형 공개(progressive disclosure) 덕분에 큰 스킬 라이브러리가 있어도 컨텍스트 창을 바로 잠식하지 않는다는 설명이다. 본문 말미에는 인덱스가 약 3k 토큰 수준이라고도 적혀 있다.

실무에서는 어디에 쓰일까

예시가 구체적이다. 내부 API 온보딩에서는 사내 문서 URL을 `/learn`에 넘겨 인증, 페이지네이션, 자주 쓰는 호출을 다루는 스킬로 만들 수 있다. 배포 런북도 한 번 같이 수행한 뒤 `/learn how I just deployed the staging server`처럼 굳힐 수 있다.

또한 여러 스킬을 묶는 번들(bundle)도 지원한다.

  • 예시 YAML: `backend-dev`
  • 포함 스킬: 코드 리뷰, 테스트 주도 개발, PR 워크플로
  • 추가 instruction: 항상 실패 테스트부터 작성

즉 지식 조각을 단일 스킬로 남기는 데서 끝나지 않고, 반복 업무 단위를 조합 가능한 작업 세트로 관리하려는 방향이다.

운영 관점에서 볼 포인트

별도 인제스트 엔진이 없다는 점은 장점이자 제약이다. 장점은 CLI, TUI, 메시징 게이트웨이, 대시보드, 로컬·Docker·원격 터미널 백엔드에서 같은 방식으로 동작한다는 점이다.

저장은 `skill_manage` 도구를 통해 이뤄진다. `write_approval`을 켜 두면 새 스킬은 바로 반영되지 않고 `~/.hermes/pending/skills/`에 대기시켜 검토할 수 있다.

사내 도입에서는 이 승인 흐름이 중요하다. 에이전트가 배운 절차가 팀 표준과 다를 수 있기 때문에, 지식 축적 기능은 곧바로 거버넌스 문제와 연결된다.

확인할 리스크

스킬 문서가 표준 형식을 따른다고 해서, 내용의 정확성이 자동으로 보장되는 것은 아니다. 특히 대화에서 배운 절차는 당시 맥락에 최적화된 우회로일 수 있고, 시간이 지나면 금방 낡을 수 있다.

또한 스킬은 메모리와 다르다. 메모리는 항상 컨텍스트에 있어야 할 작은 사실이고, 스킬은 필요할 때만 읽는 절차 문서다. 둘을 혼용하면 에이전트가 언제 무엇을 불러야 하는지 판단이 흔들릴 수 있다.

실무에선 스킬 작성 후 검증 섹션과 실패 모드 문서를 함께 두는 운영 규칙이 필요해 보인다.

출처와 한계

발췌에는 `/learn`의 생성 품질 평가나 실패율 같은 정량 지표는 없다. 따라서 기능의 유용성은 충분히 보이지만, 대규모 팀 환경에서의 일관성은 별도 검증이 필요하다.
