GLM-5.2 API, 어디까지 제어되나

실무에서 모델 도입은 성능 수치보다 API 제어면이 더 빨리 문제를 일으킨다. 이 가이드는 GLM-5.2를 예시로, 단순 채팅을 넘어 사고 모드 on/off, 노력도 단계, 스트리밍 추론 채널, 툴 루프, 비용 계산까지 하나의 재사용 래퍼로 정리한다. 특히 OpenAI 클라이언트를 그대로 쓰면서 공급자별 확장 옵션을 `extra_body`에 넣는 방식이 중심이다. 모델 평가 기사라기보다 운영 코드의 설계 선택을 보여주는 문서로 읽는 편이 맞다.

핵심은 모델보다 래퍼다

가이드의 출발점은 GLM-5.2 자체보다, 이를 감싸는 재사용 가능한 채팅 래퍼다. 여러 공급자 옵션을 딕셔너리로 두고, 환경변수에서 API 키를 안전하게 읽어 OpenAI 클라이언트를 초기화한다.

지원 예시는 다음과 같다.

  • Z.ai
  • OpenRouter
  • Together
  • Requesty
  • Hugging Face Router

가격 추적도 함께 넣었다. 예시 코드에서는 입력 100만 토큰당 1.40달러, 출력 100만 토큰당 4.40달러를 기준으로 누적 사용량을 계산한다.

무엇을 제어할 수 있나

핵심 래퍼 `chat()`은 단순 메시지 전송을 넘어 여러 운영 옵션을 통합한다.

  • thinking: enabled / disabled
  • reasoning_effort: `high` 또는 `max`
  • stream: 스트리밍 여부
  • tools, tool_choice: 함수 호출 설정
  • tool_stream: 도구 스트리밍 옵션

GLM 전용 설정은 `extra_body`에 실어 OpenAI 호환 클라이언트에서도 그대로 보낼 수 있게 했다. 이 방식은 공급자 종속 옵션이 라이브러리 표면을 오염시키지 않게 해 준다.

추론 채널과 답변 채널을 분리해서 다룬다

가이드는 GLM의 숨겨진 추론 흔적을 `reasoning_content` 필드에서 꺼내는 헬퍼를 둔다. 메시지 객체, 스트리밍 델타(delta), 또는 `model_extra`에서 값을 찾도록 해 공급자 차이를 흡수한다.

스트리밍 예시에서는 추론 채널과 최종 답변 채널을 별도로 출력한다. 즉 사용자는 모델이 생각하는 텍스트와 실제 응답을 분리해 UI나 로그에 반영할 수 있다.

이 설계는 디버깅에는 유용하지만, 서비스 UI에 그대로 노출할지는 별도 판단이 필요하다. 원문도 어디까지나 실습용으로 채널 분리를 보여준다.

함수 호출은 한 번으로 끝나지 않는다

함수 호출 예시는 계산기와 도시 인구 조회 두 도구를 등록하고, 모델이 툴 호출을 내놓으면 실행 결과를 다시 대화에 넣어 반복하는 풀 루프(full loop) 방식이다.

도구 스펙은 JSON 스키마 형태로 선언한다.

  • `calculator(expression: string)`
  • `city_population(city: string)`

그리고 실행 단계에서는

  • 인자 JSON 파싱
  • 실제 함수 실행
  • `tool` 역할 메시지로 결과 주입
  • 추가 도구 호출이 없을 때 종료

라는 구조를 따른다.

즉 함수 호출은 단일 API 옵션이 아니라, 대화 상태 머신으로 다뤄야 한다는 점을 코드로 보여준다.

실무에 바로 참고할 부분

이 가이드가 유용한 이유는 '데모를 위한 데모'를 넘어 운영에 필요한 잔업을 같이 다루기 때문이다.

  • 멀티 프로바이더 전환을 환경변수로 분리
  • 토큰 사용량 누적 추적
  • 사고 모드와 지연·출력 토큰의 상관관계 관찰
  • 구조화 JSON 출력 및 장문 검색 테스트
  • 소형 도구 사용 에이전트 구성

사내에서 여러 모델 공급자를 동시에 평가할 때, 같은 인터페이스로 감싼 뒤 확장 필드만 별도 레이어에 넣는 패턴은 그대로 재사용할 수 있다.

확인할 리스크와 빈칸

이 글은 튜토리얼이라 모델 자체의 정식 벤치마크, 라이선스, 컨텍스트 한도, 배포 제약을 체계적으로 설명하지는 않는다. 일부 가격과 모델명은 예시 코드에 들어 있지만, 전체 제품 스펙 문서로 보기는 어렵다.

또한 reasoning trace를 읽어 올 수 있다고 해서, 모든 공급자가 동일한 필드와 동일한 안정성으로 이를 반환한다는 뜻도 아니다. 코드 자체가 여러 경로를 시도하는 점이 오히려 그 차이를 보여준다.

사내 적용 시에는 API 호환성만 보지 말고, 공급자별 응답 필드·오류 형식·사용량 집계 차이를 따로 검증해야 한다.

출처와 한계

실습형 튜토리얼 발췌라서 후반부의 장문 검색, 구조화 출력, 비용 추정 세부 결과는 일부만 보인다. 따라서 GLM-5.2의 절대 성능 판단 자료로 쓰기보다, OpenAI 호환 추상화와 툴 루프 구현 예제로 읽는 편이 적절하다.
